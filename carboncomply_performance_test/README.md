# CarbonComply Performance Test

This folder contains the performance evaluation of the CarbonComply pipeline, as reported in the associated article. The test measures the time needed to transform an increasing number of Communication templates into RDF and XML, and validates the generated outputs against the [SHACL shapes](../SHACL/astrea-shapes.ttl) and the official [CBAM XSD schema V19](../carboncomply/CarbonComply-rest/resources/xml_cbam/v19).

## What the test does

The input folder `input_synthetic_cbam_templates/` contains synthetic CBAM templates generated by Claude (Sonnet 5 model). The test processes them incrementally: first with 1 file, then with 2 files, and so on until all files are included. For each number of files:

1. The CarbonComply pipeline is executed 5 times, and the runtime of each execution is recorded.
2. The average runtime is computed.
3. The number of triples in the generated RDF graph is counted.
4. The generated RDF is validated against the [SHACL shapes](../SHACL/astrea-shapes.ttl) using the Java SHACL validator included in this folder.
5. The generated XML is validated against the [CBAM XSD schema V19](../carboncomply/CarbonComply-rest/resources/xml_cbam/v19).

Only the pipeline execution (step 1) is timed. The validation steps are performed afterwards and do not affect the reported runtimes.

## Requirements

- **Python 3.12 or later**
- **JDK 21 or later**, required to build and run the SHACL validator

You can check your versions with:

```bash
python3 --version
java -version
```

## Folder structure

The test relies on other folders of this repository, so it must be run from within the full repository:

```
<repository root>/
├── carboncomply/
│   └── CarbonComply-rest/          # Backend: pipeline, mappings, ontologies, XSD schema
├── cbam-network/                   # Ontologies
├── SHACL/
│   └── astrea-shapes.ttl           # SHACL shapes used for validation
└── carboncomply_performance_test/  # This folder
    ├── input_synthetic_cbam_templates/
    ├── shacl-validator-0.0.1.jar   # Java SHACL validator
    ├── output/                     # Created when the test runs
    ├── performance_test.py
    ├── requirements.txt
    └── README.md
```

## Running the test

All commands below are run from the `carboncomply_performance_test/` folder.

### 1. Create the Python environment

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

On Debian/Ubuntu, if the first command fails because `ensurepip` is not available, install the venv package first (`sudo apt install python3-venv`).

### 2. Run the test

```bash
python performance_test.py
```

The script checks that Java is available before starting. Progress is printed to the console. Depending on the hardware, the full test may take a considerable amount of time, since the pipeline is executed 5 times for every number of input files.

When finished, you can leave the virtual environment with `deactivate`.

## Output

Results are written to the `output/` folder:

- `output/performance.tsv` contains one row per number of input files, with the following columns: number of files, the runtime of each of the 5 executions (in seconds), the average runtime, the number of generated triples, the SHACL validation result, and the XSD validation result.
- `output/<N>_files/` contains the files generated by the pipeline when processing `N` input files.

## Running the SHACL validator on its own

The validator can also be used independently to validate a single RDF file, without running the whole performance test:

```bash
java -jar shacl-validator-0.0.1.jar -i <data.ttl> -s ../SHACL/astrea-shapes.ttl
```

This validator is an independent proyect available at [https://github.com/tecnomod-um/shacl-validator](https://github.com/tecnomod-um/shacl-validator)

## Implementation note

The backend mapping files (YARRRML) reference ontologies using paths relative to the backend folder (for example, `resources/ontologies/CNCode.ttl`). For this reason, the test script changes its working directory to `carboncomply/CarbonComply-rest` before running the pipeline. All paths used by the test itself are absolute, so this does not affect the location of the input and output files.
